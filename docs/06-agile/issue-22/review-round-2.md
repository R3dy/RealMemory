## Comments *(required for every FAIL — each specific and actionable)*

### [2]-C1 — The verification §4.1.1 defers is already answered: `chat.message` never fires for assistant messages in the installed host, and the named fallback events don't exist
**Plan section:** §4.1.1, §9 A22.3 (scope, criteria, §3a), §10
**Problem:** Round-1 C1 asked the plan to stop assuming and to verify + name a fallback; the architect added the verification machinery (verified fixed above). But round-2 due diligence answered the question outright. Inspecting the installed OpenCode binary (`~/.opencode/bin/opencode`, 2026-08-09 — the "version in use" this plan targets): `trigger("chat.message", ...)` appears **exactly once**, in `SessionPrompt.createUserMessage`, with `{message: <the newly created role:"user" message>, parts}`. There is no assistant-side `chat.message` trigger. There is also no `chat.message.completed` or `session.turn.end` event anywhere in the build — the fallback's example event names are wrong. What does exist: the `message.updated` / `message.part.updated` **events** (published via the bus; the assistant message is updated on completion) and `session.idle` (verified-firing; already used by this plugin). So the plan's "primary trigger" is known-dead code in the real host, the fallback that will actually carry the headline feature is sketched with non-existent event names, and A22.3's criteria/scripts still target the dead path (e.g. the criterion "the `chat.message` assistant branch runs on a detached promise"; §3a step 5 firing a fake `role:"assistant"` chat.message). Two further hazards if built as written: (a) a Worker who adds the assistant branch *and* the event fallback creates a double-fire risk the day a future OpenCode version does fire `chat.message` for assistant messages (double metrics, double stores — dedup blunts the stores, not the metrics); (b) the Validator will be asked to check criteria naming a branch the implementation may not have. Note the issue's own mapping never proposed `chat.message` for the post-turn side — it says "`event`: monitor turn completion and trigger post-turn update" — so promoting the event branch to primary also *aligns* the plan with the issue.
**Required change:** Rewrite §4.1.1 to bake in the verified answer: state that `chat.message` fires only for user-message creation in the current OpenCode (with the evidence), and make the **primary** trigger an `event`-handler branch keyed on `message.updated` where the message is `role: "assistant"` and complete/finished (Worker pins the exact completion predicate and payload shape — text from the event properties or `ctx.client.messages` — and documents it in the PR), with `session.idle` as the degradation fallback. Keep or drop the `chat.message` assistant branch deliberately: if kept as future-proofing, add an explicit guard so only one trigger runs `evaluateDelta` per turn. Update A22.3's criteria and §3a so the detached-promise, error-safety, and integration assertions name the actual wired trigger (the fake-context step fires the chosen event, not a fake assistant `chat.message`), and fix the muddled `lastAssistantText` parenthetical (the user branch cannot stash assistant text). The §4.1.1 discussion of the issue's `event` mapping should now say the plan *follows* it.

### [2]-C2 — The pinned user-branch order resets `lastToolCapture` to null *before* `classifyIntent` reads it — the `tool_outcome` intent is unreachable in production
**Plan section:** §4.1.2 (`lastToolCapture` "Cleared at the start of the next user message"), §4.1.6 (reset code placed "before classify/push"), §9 A22.3 (user-branch modify list; criteria; §3a)
**Problem:** A22.3 pins the user-branch order as: extract text → **reset per-turn state (`lastToolCapture = null`, `lastInjectedMemoryIds = null`)** → `classifyIntent(currentUserText, "", recentUserTexts, lastToolCapture)` → push. `lastToolCapture` is only ever set by `tool.execute.after`, which runs during the *assistant's* tool loop — i.e. strictly after the user branch for that turn has already executed. So at classification time the field has always just been nulled by the same handler execution, `classifyIntent`'s 4th argument is always `null` in production, and the `tool_outcome` branch can never fire. The unit criterion (`classifyIntent("thanks", "", [], {tool: "bash", ...})` → `"tool_outcome"`) still passes because it injects the parameter directly, and no Experience Script exercises the path end-to-end (A22.3 §3a steps 5-6 fire no tool execution; A22.6's E2E fires none either) — so the defect ships silently. This is the same temporal class of bug as round-1 C2 (reading state after it's cleared), reintroduced by the C4 fix's reset placement. (The `lastInjectedMemoryIds` reset is fine — it's read in a *later* hook, not the same one.)
**Required change:** Pin the order as **classify first (against the prior turn's `lastToolCapture`), then reset** — e.g. move the `lastToolCapture = null` clear to after the `classifyIntent` call in the user branch (or clear it in `evaluateDelta` after use); update §4.1.2's "cleared" note and §4.1.6's reset snippet to match. Add an A22.3 acceptance criterion and a §3a step that fire `tool.execute.after` (e.g. a bash error) and then the next user message, and assert a `tool_outcome` memory was stored with the §4.1.5 template content (`"Tool outcome (bash): error — …"`) — a test that fails against the currently-pinned order.

### [2]-C3 — Intent-layer file paths are ambiguous (repo vs. workspace), and §11's "git revert removes them" claim is false
**Plan section:** §4.5 ("Intent-layer updates"), §9 A22.1 (scope, criteria, §3a) + A22.6 (scope), §11 (Rollback, intent-layer bullet)
**Problem:** The ADR collection, DECISIONS.md, SYSTEM_MAP.md, and INVARIANTS.md live in the **workspace** at `PROJECTS/realmemory/docs/` (ADR-001…007 are there; the repo README links to them as `../docs/adr/…`). The repo (`PROJECTS/realmemory/repo`, the only git tree — the workspace is unversioned) contains **no** `docs/adr/`, no `docs/DECISIONS.md`, no SYSTEM_MAP/INVARIANTS. The plan writes bare relative paths (`docs/adr/ADR-008-brain-loop-behavior.md`, `docs/DECISIONS.md`) while the Worker operates in the repo — a literal Worker creates `repo/docs/adr/ADR-008` (splitting the ADR collection) and a `repo/docs/DECISIONS.md` (forking the intent layer), and the Validator's criteria then verify the wrong tree. The plan is internally inconsistent: A22.1 uses the workspace-absolute `PROJECTS/realmemory/PARKING_LOT.md` in the same breath as bare `docs/DECISIONS.md`. Compounding it, §11 asserts the ADR-008 file and the DECISIONS/SYSTEM_MAP/INVARIANTS updates "are inside the PRs — `git revert` removes them": they are not in the PRs (wrong tree, unversioned workspace), so the documented rollback silently leaves a stale intent layer claiming ADR-008 exists after the code is gone — the exact bookkeeping corruption round-1 C5 guarded against.
**Required change:** (a) State the absolute workspace paths everywhere (`PROJECTS/realmemory/docs/adr/ADR-008-brain-loop-behavior.md`, `PROJECTS/realmemory/docs/DECISIONS.md`, etc.) and say explicitly these files live outside the repo and outside the PRs. (b) Fix §11's intent-layer bullet: revert of those files is a manual edit (restore the Drift #1 Open Item, remove the ADR-008 row, delete the ADR file) performed alongside the `git revert`, not by it. (c) Adjust A22.1's "no code changes — docs only" criterion so the Worker/Validator know `npm run check` is run in the repo while the edited files are in the workspace.

### [2]-C4 — The `brainLoop` config knob is declared, validated, and ADR-ratified, but nothing consumes it
**Plan section:** §3 (config anchor), §4.5(h), §9 A22.2 (knobs) + A22.3 (scope)
**Problem:** A22.2 adds `brainLoop: true` to `DEFAULTS`/`MemoryStoreConfig`/`validateConfig`, and ADR-008(h) ratifies the config knobs — `brainLoop` named explicitly — as a **stable public config surface**. But no story wires a consumer: §4.1.1's trigger pseudocode has no `if (!config.brainLoop) return`, and A22.3's user-branch/assistant-branch modify lists never mention it. Compare the existing pattern the codebase already uses: `tool.execute.after` returns early when `autoCapture === false` (`plugin.ts:388-389`). As specified, the knob ships inert — a documented public contract that does nothing, which is worse than absent (a user setting `brainLoop: false` gets a silently ignored setting, and ADR-008 has promised its stability).
**Required change:** Name the consumer in the plan: the delta-loop trigger (whatever [2]-C1 settles) checks `config.brainLoop !== false` before running `evaluateDelta`, and state whether the user-branch `dynamicLimit`/classification work is also gated (recommend: gate the whole #22 per-turn path, leaving the pre-#22 fixed-`limit: 3` recall behavior as the disabled state). Add an A22.3 criterion: with `brainLoop: false`, firing the trigger stores nothing and records no metrics. Alternatively, drop the knob from A22.2 and ADR-008(h).

## Verdict

**VERDICT: NEEDS CHANGES** — comments [2]-C1…[2]-C4 must be resolved; architect revises and resubmits for round 3.

**Summary:** All six round-1 comments are verified fixed, and the revision is substantially stronger — the PluginState contract, content templates, ADR-008 surface, and story order are now solid, and every re-checked citation held. But round-2 verification against the installed OpenCode binary settled the question round 1 only flagged: `chat.message` fires solely for user messages, so the plan's primary trigger is known-dead and the real path (the `message.updated` event branch the issue itself recommends) must be promoted from a vaguely-named fallback to the specified primary ([2]-C1). All four are mechanically fixable in one revision round.
