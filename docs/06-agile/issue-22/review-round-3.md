## Notes (non-blocking — advisory to the Worker, not conditions of approval)

1. **Delta-before-summarization placement is load-bearing.** The existing `session.idle` block returns early at `plugin.ts:313-322` when `autoSummarize`/`summaryProvider`/`sessionID` is absent (the default — summarization is opt-in). The plan's §4.1.1 pseudocode correctly places the delta block at the TOP of the branch, before those returns. A Worker who instead appends the delta code at the bottom of the existing block would silently gate the headline feature behind summarization being configured. The pseudocode is right; the PR reviewer should check the diff honors it.
2. **`state.config` can be null pre-init.** The `brainLoop` gate pseudocode reads `state.config.brainLoop === false`; the existing code treats config as nullable (`state.config as {...} | null` with optional chaining at :388-389) because `getStore()` is what loads it. The Worker should mirror the optional-chaining pattern (`state.config?.brainLoop === false`) — a literal transcription placed before the branch's first `getStore()` could throw.
3. **`recall_hit_rate` on the primary trigger.** Accepted as a documented trade-off: with `assistantText=""`, injected turns record `recall_miss`. If this proves misleading in practice, the natural follow-up is for the detached `evaluateDelta` to fetch the last assistant message via the same `fetchSessionTranscript(ctx, sessionID)` mechanism the summarization path already uses in the same branch (:332) — a future increment, not this plan's problem.
