## Comments *(required for every FAIL — each specific and actionable)*

### [1]-C1 — The assistant branch of `chat.message` is an unverified firing assumption, and it carries the headline feature
**Plan section:** §3 (Flows), §4.1, §9 Story A22.2
**Problem:** The entire per-turn delta loop — gap item 1, the point of the issue — is inserted as `else if (role === "assistant")` in the `chat.message` handler. Nothing in the plan verifies that OpenCode's `chat.message` hook actually fires for assistant messages (the current code's early return at `plugin.ts:456` is a *guard*, not evidence the hook fires with `role: "assistant"`), nor that the assistant text arrives as `output.message.content` / `output.parts` in the shape §4.1's pseudocode assumes. The plan itself demonstrates why this is fatal: §4.4 cites the Epic #3 lesson — "`message.updated` was an Event, not a hook, and never fired — wiring it as a hook silently did nothing" — and correctly adds a Worker verification step for `experimental.session.compacting`. The same verification discipline is missing for the far more load-bearing assistant branch; if it never fires, A22.2/A22.3 ship tests that pass against a fake context while the feature does nothing in a real host. Compounding this, the issue's own recommended mapping puts post-turn updates on `event` ("monitor turn completion and trigger post-turn update") — the plan deviates from the issue's mapping without discussing it or naming a fallback.
**Required change:** Add to §4.1 (and A22.2's scope) an explicit Worker verification step, mirroring §4.4's compacting caveat: confirm from the OpenCode plugin API (source or docs of the version in use) whether `chat.message` fires for assistant messages and what the payload shape is; if it does not fire, name the fallback trigger (e.g. a turn-completion `event` branch per the issue's own mapping, or `message.updated`/`message.part.updated` as Events) and wire `evaluateDelta` to that instead. State in §4.1 that the issue's `event`-based mapping was considered and why the chosen trigger is equivalent or better. Add to A22.2's Experience Script a live-host smoke step (or an explicit note that real-host firing was verified and how), so the Experience Runner PASS is not based solely on a fake context.

### [1]-C2 — `recall_hit_rate` as specified reads `state.pendingInjection` after `experimental.chat.system.transform` has already cleared it
**Plan section:** §4.1 step 6 (metrics), §9 A22.2 criteria, §10 `tests/plugin-brain-loop.test.ts`
**Problem:** §4.1 step 6 defines the hit signal as "`state.pendingInjection` was non-null when the assistant message arrived (i.e. a memory was injected into this turn's system prompt)". But the delivery hook clears the staged block every time it fires — verified at `plugin.ts:497-510` (`output.system.push(state.pendingInjection); state.pendingInjection = null;`). Delivery happens when the system prompt is built for the turn, i.e. *before* the assistant responds. Therefore, at assistant-message time, `pendingInjection` is **always null** on exactly the turns where an injection occurred — the metric records `recall_miss` on every injected turn and the flagship observability number is garbage. Unit tests written against the current spec will pass while the metric is meaningless end-to-end.
**Required change:** Change §4.1 to carry injection state across the turn: e.g. add `state.lastInjection: { memoryIds: string[]; text: string } | null`, set by `experimental.chat.system.transform` at delivery time (before clearing `pendingInjection`) and cleared at the start of the next user turn; define the hit check against `state.lastInjection`. Update A22.2's acceptance criteria and the E2E criterion in A22.5 (§3a step 9) so they assert a `recall_hit` is recorded on a turn where an injection was actually delivered — a test that would fail against the current spec.

### [1]-C3 — The delta-memory `content` derivation is unspecified for a no-LLM path
**Plan section:** §4.1 step 3, §9 A22.2 (criteria + §3a)
**Problem:** §4.1 step 3 says the stored `content` is "a concise summary derived from `userText` (the correction / preference / repetition phrased as a behavior-oriented memory)". The plan forbids an LLM here (correctly — INV-017, Drift #5), which means the derivation must be a deterministic string rule, but no rule is given. Two Workers will produce two different formats; worse, the acceptance criteria can't pin it down — "content referencing the correction" (A22.2 §3a step 5) is judgment-call language, the exact thing the build loop's "no 'works correctly'" rule exists to prevent. It also matters functionally: the content string is what `findDuplicate` matches future deltas against (INV-018), so an ad-hoc format silently changes dedup behavior.
**Required change:** Specify the exact content template per intent in §4.1 (e.g. `correction` → `"User corrected the agent: <userText>"`, `preference` → `"User preference: <userText>"`, `repetition` → `"Repeated request: <userText>"`, `tool_outcome` → the `state.lastToolCapture` summary), then tighten the A22.2 criteria to assert the stored content equals/matches the template output for a given input.

### [1]-C4 — The `PluginState` contract is incomplete and the repetition detection is order-ambiguous
**Plan section:** §4.1 (PluginState additions, `classifyIntent`), §9 A22.2 (scope + criteria)
**Problem:** Four holes in the state contract: (a) `classifyIntent`'s `tool_outcome` branch reads `state.lastToolCapture`, but §4.1's declared PluginState additions are only `lastUserText` and `recentQueries` — `lastToolCapture` is never declared, no story adds it, and its turn-scoping ("set … in the same turn") is undefined (when is it cleared?). (b) A22.2's scope lists the user-branch order as "stash … push to `state.recentQueries` → compute `intent`": if the current message is pushed into the ring buffer *before* classification, it matches itself and every message classifies as `repetition` (dynamicLimit 4 and a `task_pattern` store on nearly every turn). (c) The acceptance criterion `classifyIntent("the save button is broken", "", ["the save button is broken"])` → `"repetition"` is annotated "same query seen twice in recentQueries" but the array contains it **once** — the count semantics (≥1 prior sighting vs. >1 including current) are not pinned. (d) `evaluateDelta(store, state, state.lastUserText, …)` is called with `lastUserText: string | null`; no criterion covers the assistant-message-with-no-prior-user-text case (session start, or a missed user hook).
**Required change:** In §4.1/A22.2: declare `lastToolCapture` (type, who sets it, when it clears — e.g. set on a `tool.execute.after` store, cleared at the next user message); pin the order as *classify against history first, then push* (or equivalently define repetition as "≥1 match in the buffer excluding the current message"); rewrite the criterion to match the pinned semantics (e.g. `classifyIntent("X", "", ["X"])` → `"repetition"` under the "seen before" rule); add a criterion that `evaluateDelta` returns without storing when `lastUserText` is null.

### [1]-C5 — ADR-008 as specified does not cover the Drift #1 surface the plan claims it resolves
**Plan section:** §4.5, §9 A22.5 (criteria), §6 (DECISIONS.md update)
**Problem:** DECISIONS.md's Open Item for Drift #1 states the brain-loop ADR must define "the OpenCode plugin's role, its public-vs-private boundary, the non-blocking hook contract (INV-017), **or whether its config knobs … are a stable public config surface**." §4.5's specified ADR-008 content covers the five #22 behaviors (heuristics, auto-relate cap, metrics table, compacting hook, conciseness) but says nothing about the plugin's role, the public/private boundary, or the config-surface question — and A22.5's acceptance criteria only require the ADR to state the decision/options/consequences and note "does NOT supersede ADR-003 / does NOT add LLM calls." Yet A22.5 then marks Drift #1 "**resolved by ADR-008**" in DECISIONS.md and SYSTEM_MAP.md. Marking an Open Item resolved with an ADR that doesn't address its stated surface corrupts the intent layer's bookkeeping — the next Cartographer refresh will re-flag it as drift.
**Required change:** Either (a) expand the ADR-008 content specified in §4.5 (and the A22.5 criteria) to cover the full Drift #1 surface — plugin role, public-vs-private boundary, INV-017 contract ratification, and an explicit statement on whether the plugin config knobs are a stable public surface — or (b) scope the resolution claim honestly: ADR-008 resolves Drift #1 *for the brain-loop behaviors it enumerates*, and DECISIONS.md/SYSTEM_MAP.md updates say exactly that, leaving the remainder open.

### [1]-C6 — Story order lands the new hooks and config knobs four PRs before the ADR that is supposed to authorize them
**Plan section:** §9 (story order A22.1 → A22.5)
**Problem:** DECISIONS.md's "Issue #22 — Anticipated intent conflicts" #1 states: "An agent must not expand the plugin's hook surface or add new config knobs without that ADR." Under the build loop's per-story PR cadence, A22.1 adds four config knobs (`concisenessCap`, `autoRelate`, `brainLoop`, `compactingIntervalHours`), A22.2 adds the assistant hook branch, and A22.4 adds the compacting hook — all merged before ADR-008 exists (A22.5). The plan never addresses this ordering against the intent layer's own gate condition.
**Required change:** Reorder so the ADR lands first or with the first surface change (e.g. author ADR-008 in A22.1, or split A22.5 so the ADR precedes the knob/hook stories and the docs-sync/tool/endpoint work remains last), **or** state explicitly in §9 that the five stories merge as one gated unit (no per-story merge to `main` until A22.5 completes), so no commit reaches `main` that expands the surface without its ratifying ADR.

## Verdict

**VERDICT: NEEDS CHANGES** — comments [1]-C1…[1]-C6 must be resolved; architect revises and resubmits for round 2.

**Summary:** The plan's evidence is unusually well-grounded — every file:line citation I checked held (one off-by-one), the intent-layer table is accurate, scope discipline around Drifts #5/#6/#7 is clean, and the rollback reasoning is verifiably correct against the migration runner. But the headline feature rests on an unverified hook-firing assumption of exactly the class this project has been burned by before (C1), the flagship metric reads state that is always cleared before it is read (C2), three Worker-facing specification holes would each force invented behavior (C3, C4), and the ADR-008 resolution claim overreaches its specified content and lands four PRs late (C5, C6). All six are mechanically fixable in one revision round.
